# Архитектура и техническая реализация

Этот документ описывает, **как реализуется текущая версия**: среду, стек, архитектуру, запуск, проверки и размещение. При смене среды разработки технические решения можно пересмотреть, сохраняя требования приложения.

- Требования и утверждённые вопросы: [спецификация](automotive_book_of_changes_spec.md).
- Дизайн-система и внешний вид: [UI_SPEC.md](UI_SPEC.md).
- Порядок работ и состояние приёмки: [TODOs.md](TODOs.md).
- Фактическая схема существующего каталога: [data/README.md](data/README.md).

## Состояние реализации

В M2 реализовано полное интервью в согласованном интерфейсе M1: 12 основных вопросов, необходимые ситуационные уточнения и прямые вопросы, вычисление шести битов и выбор одной из 64 записей каталога. После вопроса 12 открывается результат либо первое нужное уточнение без промежуточного экрана. Оба вида дополнительных вопросов продолжают общую шкалу до 12 сегментов.

Возврат восстанавливает выбор. Изменение ответа пересчитывает маршрут и удаляет ответы на исключённые дополнительные вопросы; при повторном появлении они задаются заново. Служебная панель, селектор палитры и переходы по демонстрационным экранам удалены. Рабочая палитра — graphite (№ 2); три палитры и цветовые роли сохранены.

Ответы и результат хранятся только в памяти текущей страницы. Постоянное сохранение — M4, PWA — M5. M1 и M2 приняты пользователем 21 октября 2026; статус — в TODOs. Следующий этап M3 — проверка на телефоне и доводка. Каталог и галерея остаются отдельными материалами. Коммиты и публикация — только по явной просьбе.

### Организация оформления

Дизайн-система, семья шрифта, размеры, цвета, компоненты и адаптивность описываются в [UI_SPEC.md](UI_SPEC.md). В архитектуре фиксируются только способы реализации этих решений.

- Общие реестры `fonts`, `palettes`, `colors`, `typography`, базовый reset подключаются из `src/main.tsx` один раз. CSS компонентов содержит геометрию, состояния и ссылки на именованные цвета; семейство/размер/вес/интервал текста задаются только классами `type-*`. Базовые значения цветов находятся только в `palettes.css`; `colors.css` содержит роли и смешения текущей темы без литералов и прямых ссылок на отдельные палитры. Все экраны, состояния и диалоги используют выбранную тему. Тема задаётся `data-palette`; в приложении используется `graphite`, пользовательского переключателя нет. `data-view` и `theme-color` отражают фон результата выбранной темы; начальное значение метатега HTML — технический fallback, не отдельный цвет компонента.
- Manrope подключён локально через `@fontsource-variable/manrope` 5.3.0. Два WOFF2 для кириллицы и латиницы весят около 39 КБ; внешних запросов к Google Fonts нет.
- Лицензия шрифта копируется в сборку как `assets/Manrope-LICENSE`. При реализации PWA используемые файлы шрифтов включаются в офлайн-ресурсы вместе со стилями.
- Главная вынесена в `src/HomePage.tsx`; её геометрия — `home-*`, типографика — общий реестр. Hero преобразован из PNG в WebP с качеством 90 без изменения размеров (1672 × 941, 213 622 байта); SVG хранится отдельным файлом и окрашивается CSS-маской. Arial, системный шрифт и локальный Manrope используются по принятым профилям UI_SPEC, без скрытой подмены семейств. Исходники и исторические HTML остаются в `design/`, в сборку не включаются.
- `App` управляет маршрутом и состоянием. Главная, интервью, результат и оба диалога имеют отдельные компоненты; `useModalDialog` обслуживает оба окна. Неиспользуемые стили прежних вариантов удалены. В каждом CSS сначала базовые правила, затем адаптивность и состояния движения; повторное добавление правил для исправления каскада не заменяет редактирование исходного блока.
- Перед завершением изменений оформления запускать `npm.cmd run check:ui` и `npm.cmd run build`. Проверка не добавляет зависимостей и не меняет UI; фиксирует отсутствие цветов вне реестров, текстовых свойств в геометрии, неопределённых переменных, повторных деклараций, неиспользуемых/недокументированных `type-*`. Визуальные и браузерные проверки дополняют её; это не автоматическое подтверждение доступности всего приложения.

## Подключение подготовленного контента

Расшифровка получает неизменённый текущий результат из `App`. Код выводится группами в исходном порядке; признаки — индексами `[5,4,3]`, затем `[2,1,0]` из `bits` и `preferences`, собранных загрузчиком из `axisWording`. Общий `HexagramLine` рисует непрерывную/разорванную полосу и для квадрата результата, и для строк диалога; геометрия квадрата не изменена. Ручного набора 64 расшифровок нет.

Окно — `<dialog>.showModal()`: фон inert, имя/описание заданы ARIA. Фокус сначала на заголовке; Tab/Shift+Tab удерживаются между крестиком и прокручиваемой областью. Шапка вне внутренней прокрутки. Esc перехватывается через `cancel`, нажатие снаружи проверяется по координатам начала и конца, чтобы перетаскивание изнутри не закрывало окно. Состояние открытия одно, повторный клик не дублирует диалог. На время открытия фиксируется body с компенсацией полосы прокрутки; при закрытии/размонтировании точно восстанавливаются его inline-стили, положение страницы и фокус открывшей кнопки с `preventScroll`. Cleanup работает и при повторном выполнении эффектов React StrictMode.

`loadResult(bits, signal)` в `src/data.ts` загружает пять JSON каталога и вызывает `validateCatalog` и `lookupCar` из `src/catalog.ts`. Проверяются порядок осей, все 64 кода и уникальные назначения автомобилей, связи, обязательные тексты, пояснения и локальные пути фотографий. `lookupCar` преобразует профиль в ключ `RRR-CCC` и возвращает существующую запись. Фиксированного Fiat и демонстрационного загрузчика больше нет. Ошибки показываются с повторной загрузкой; запрос при уходе отменяется через AbortController.

Результат отрисовывается отдельной веткой `App` без прежнего каркаса и служебной панели. `data-view` и `theme-color` меняют фон окна и браузерной панели на светлый, после выхода восстанавливается игровая тема. SVG гексаграммы использует `y = 48 − 8 × index` для битов в исходном порядке: первый внизу, шестой наверху. SVG имеет `viewBox="0 0 60 60"`, CSS-размер 60 × 60 px, полосы высотой 4 px и `shapeRendering="crispEdges"`; координаты кратны целым CSS-пикселям. Существующий Header 1 главной вынесен в `.type-heading-1` и применяется также к архетипу без изменения вида главной. Header 2 `.type-heading-2` используется для разделов главной и автомобиля; настройки шрифта не дублируются в стилях карточки. Янтарное окно расшифровки v2 получает предпочтения из текущей записи и отображает их сверху вниз по осям 6→1. Возврат на главную не очищает её; новое нажатие «Начать игру» теперь очищает ответы и открывает первый вопрос, поэтому прежний результат не открывается повторно вместо новой игры. Предупреждение выхода подключено к полному состоянию интервью в M2. Диалог «Пройти ещё раз» удалён вместе с этой кнопкой как не входящий в v5.

- Каталог хранится в пяти JSON папки `data/`. Назначения из `placements.json` связывают клетку с автомобилем и фотографией; тексты берутся из `descriptions.json`.
- Подробное описание полей находится только в [справочнике данных](data/README.md). Не создавать вторую редактируемую копию каталога; сборка может копировать ресурсы автоматически.
- Формат ключа клетки — `RRR-CCC`: оси 1–3 слева направо образуют `RRR`, оси 4–6 — `CCC`. Позиции в `structure.json` считаются отдельно внутри каждой триграммы.
- До интеграции проверить 64 уникальных результата, полноту связей и необходимые поля. Отсутствующие значения не угадывать.
- Фотографии находятся в `assets/images/cars/`; поля `url` и `full` содержат пути относительно корня текущей галереи. При сборке приложения обеспечить корректное разрешение этих путей по адресу публикации.
- Галерея и её скрипты — отдельный инструмент просмотра подготовленной базы, не часть приложения интервью. Интерфейс приложения создаётся самостоятельно: он использует JSON и фотографии напрямую, не зависит от HTML галереи или `gallery.js`, не содержит экрана галереи и не включает её в сборку. Подробная карточка автомобиля служит образцом результата по разделу 6 спецификации; её разметку и стили адаптировать в самостоятельный компонент. Общую вводную фразу брать из `descriptions.json → resultUi.twinIntro`.

## Банк вопросов

Полный банк — `data/questions.json`: `schemaVersion = 2`, `language = ru`, шесть осей `id` 1–6 с ключами из `structure.json`, четыре вопроса на ось. Роли — `core1`, `core2`, `clarifier`, `forced`; ID — `1.1` … `6.4`. Варианты: `code = A/B/C`, `value = 0/1/null`, `text`. В UI — кириллица А/Б/В; прямые вопросы содержат только A/B.

`situation` содержит только преамбулу (может быть пустой), `prompt` — только сам вопрос без повторения преамбулы. Эти тексты редактируются независимо. UI выводит `situation` обычным текстом, `prompt` — жирным; у прямого вопроса соединяет оба поля пробелом и выводит единым обычным блоком. Валидатор проверяет версию формата, оси, ключи, ID, роли, варианты, значения, непустой вопрос и тексты ответов. Повреждённый банк не запускает интервью: показывается ошибка и повторная загрузка.

Текущий источник редактируемых формулировок — JSON. При переходе к версии 2 сохранены тексты из текущего JSON, включая пользовательские правки. `npm.cmd test` проверяет структуру и алгоритм, не требует совпадения формулировок со спецификацией. `node tools/sync-questions.mjs` отдельно сравнивает JSON с разделом 5 спецификации; различия могут быть следствием более новых правок в JSON. `--write` явно заменяет банк текстами спецификации и перезаписывает такие правки; для обычного редактирования JSON эта команда не нужна. Совместимость сохраняемых сессий — M4.

`InterviewScreen` получает вопрос, номер, ответ и обработчики из `App`. Этап определяется ролью, нейтральный вариант — `value === null`. Номер берётся из актуального маршрута: 1–12 для основных и отдельный отсчёт дополнительных; прямые продолжают общую шкалу. Выбор не переключает вопрос, «Далее» требует ответа. Сохраняются защита от двойного клика/удержания клавиши, прокрутка и фокус при переходе, принятые макеты и общие резервы высоты. Длинные тексты не обрезаются; окончательная проверка читаемости на телефоне — M3.

## Архитектура интервью и сессии

Чистые функции `src/interview.ts` не зависят от React и загрузки данных:

- `getRoute(answers, bank)` — 12 основных и необходимые дополнительные вопросы в порядке осей 1–6; прямой включается после неразрешающего уточнения той же оси.
- `getNextQuestion(answers, bank)` — первый вопрос маршрута без ответа либо `null`.
- `resolveAxis(axisId, answers, bank)` — 0/1 либо `undefined`: совпадающая ненейтральная пара основных, затем минимум два совпадающих голоса из трёх, затем окончательный ответ прямого вопроса.
- `resolveProfile(answers, bank)` — шесть битов в порядке осей 1→6 либо `null` до завершения маршрута.
- `setAnswer(answers, id, answer, bank)` — новое состояние с пересчитанным маршрутом; ответы исключённых дополнительных вопросов удаляются сразу и не восстанавливаются. Нужные ответы по другим осям сохраняются.
- `lookupCar(bits, catalog)` в `src/catalog.ts` — существующая запись по ключу `RRR-CCC`.

В `App` ответы и текущий ID вопроса обновляются как единое состояние. «Назад» идёт по предыдущей записи актуального маршрута. После вопроса 12 и последнего нужного уточнения открывается следующий вопрос либо результат. Отдельно хранимого незавершённого кода нет: профиль вычисляется из ответов.

Общий `clearInterview()` очищает ответы, текущий вопрос, результат, ошибку результата и флаги диалогов. Используется «Начать игру» и подтверждённым выходом с первого вопроса. Отмена выхода сохраняет состояние и возвращает фокус. Возврат с результата на главную не очищает сессию. Запрос результата отменяется при уходе; поздний ответ не восстанавливает очищенное состояние.

Постоянное хранилище не подключено. В M4 добавить версию данных, восстановление и удаление исключённых ответов также из сохраняемой сессии.

Гексаграмма получает вычисленные биты: оси 1→6 снизу вверх, 0 — разорванная линия, 1 — сплошная. Оси 1–3 — нижняя триграмма. Пояснение использует `axisWording.row` для осей 1–3 и `column` для 4–6, показывает строки в порядке 6→1. Порядок отображения не меняет ключ каталога.

## Фотографии и отображение

- Текущие 64 файла — WebP, качество 80, длинная сторона не более 960 px. Маленькие исходники не увеличиваются; пропорции сохраняются, обрезка не применяется.
- Общий размер коллекции — 4 651 542 байта, приблизительно 4,65 МБ.
- При повторном кодировании брать исходные снимки из архива, а не уже сжатые WebP. Два архивных исходника имеют формат JPEG XL и требуют декодирования перед обработкой.
- В новой карточке v5 изображение использует `width: 100%; height: auto` и собственное соотношение сторон. Прежняя фиксированная область 4:3 отменена; снимки не кадрируются и не растягиваются.
- Для проблемных снимков обсуждать адресные исправления; не вводить 64 индивидуальных CSS-исключения для масштаба и положения автомобилей.
- Сведения об источнике, авторе и лицензии сохранять при изменении путей и кодировании.

## Сборка, PWA и обновления

- В опубликованную сборку включать интерфейс, вопросы, каталог и все 64 оптимизированные фотографии. Архив, исходные снимки и инструменты подготовки контента не включать.
- Manifest, иконки и service worker обеспечивают установку и офлайн-работу. Полный набор ресурсов кэшировать так, чтобы после подготовки были доступны любые результаты, а не только уже открытая карточка.
- Проверять завершение подготовки офлайн-ресурсов и обрабатывать прерванную загрузку. Механизм обновления должен предотвращать смешивание несовместимых версий ресурсов и данных сессии.
- Конкретные имена файлов и стратегии кэширования зафиксировать после реализации, не выдавать план за уже работающее поведение.

## Запуск и проверки

### Уже доступно: галерея

Из корня проекта выполнить `node serve-gallery.cjs` и открыть http://127.0.0.1:8765. В Windows также можно запустить `Start-Gallery.cmd`. Требуется Node.js. Сервер слушает только этот компьютер; остановка — Ctrl+C.

Галерея читает JSON напрямую, без сборки: после изменения данных обновить страницу. Прямое открытие HTML через `file://` не загружает JSON из-за ограничений браузера. Локальный сервер отдаёт корректные MIME-типы WebP и других поддерживаемых изображений.

### Промежуточные версии приложения: локальный Vite

Основной способ просмотра на всех майлстоунах — **локальный сервер Vite**. VS Code используется как редактор и место запуска терминала; сайт открывается в обычном браузере. Расширение Live Server не требуется: обработку React и TypeScript обеспечивает Vite.

Node.js и npm уже доступны на этом компьютере. Конфигурация приложения, зависимости и команды ниже подготовлены в M1. Установка зависимостей в текущей рабочей папке уже выполнена.

Порядок просмотра в Windows:

1. Открыть папку `C:\Work\Autos` в Visual Studio Code.
2. Открыть встроенный терминал: «Терминал → Создать терминал». Он должен находиться в папке проекта.
3. При первоначальной настройке выполнить `npm.cmd install`. Повторять установку нужно только при изменении зависимостей; при обычном просмотре этот шаг пропускается.
4. Выполнить `npm.cmd run dev`. Команда запускает Vite на `http://localhost:5173` и открывает браузер.
5. Оставить терминал работающим. При сохранении изменений страница автоматически обновляется; новые сборки и публикация для этого не нужны.
6. Остановить сервер сочетанием Ctrl+C в терминале. Для следующего просмотра снова выполнить команду запуска.

`npm.cmd` в Windows позволяет не зависеть от разрешения запуска PowerShell-скрипта `npm.ps1`; при работающем `npm` команды эквивалентны. Vite настроен на фиксированный порт 5173 с `strictPort`: если порт занят, он показывает ошибку, а не незаметно открывает другой адрес. Если прототип уже запущен, достаточно открыть его адрес; второй сервер не нужен.

Для повседневного просмотра есть **`Start-App.cmd`** в корне: он переходит в папку проекта, проверяет наличие Node.js и зависимостей, запускает тот же сервер и открывает браузер. После первоначальной установки зависимостей достаточно двойного щелчка. Окно сервера остаётся открытым до окончания просмотра и показывает ошибки, если запуск не удался. Это отдельный запуск приложения; `Start-Gallery.cmd` продолжает открывать галерею.

### Проверка готовой сборки локально

Для просмотра готовой сборки доступны команды:

```powershell
npm.cmd run build
npm.cmd run preview
```

Первая создаёт готовую сборку в `dist/`, вторая открывает её на локальном сервере `http://localhost:4173` (также фиксированный порт). Перед каждым просмотром изменённой сборки её нужно пересобрать. Preview служит проверке сборки на компьютере, а не публичным production-сервером. Обе команды работают без GitHub и Netlify.

`build` проверяет TypeScript и создаёт сборку. Из общего контента копируются JSON каталога, полный банк вопросов и 64 оптимизированные фотографии; архив, Markdown-документы и рабочая галерея в `dist/` не попадают. Каталог и фотографии не дублируются в исходниках приложения.

PWA ещё не реализовано. На этапе M5 проверять его на собранной версии через preview: установка, подготовка всех ресурсов, повторный запуск без сети и восстановление сессии. В режиме редактирования не включать постоянный service worker, который мог бы подменять свежие файлы старым кэшем. Для приложения и preview используются разные адреса; их хранилища и сессии независимы.

### Просмотр на телефоне

Для ежедневной проверки сначала использовать мобильный режим инструментов разработчика в браузере компьютера. Для просмотра на настоящем телефоне в той же доверенной Wi-Fi-сети предусмотреть `npm.cmd run dev -- --host 0.0.0.0` и открытие `http://<локальный-IP-компьютера>:5173` на телефоне. Компьютер должен быть включён, сервер запущен, а локальный доступ разрешён брандмауэром. Это просмотр по локальной сети без туннелей и публикации в интернете.

Просмотр по обычному HTTP в локальной сети позволяет проверять оформление и интервью, но **не заменяет проверку установки и офлайн-PWA на телефоне**. Для неё нужен защищённый адрес. В M5 при необходимости подготовить локальный HTTPS для собранного приложения с сертификатом, которому доверяет телефон. Адрес `localhost` телефона относится к самому телефону, а не к компьютеру. Публичная промежуточная публикация на Netlify для этого не планируется.

### Автоматические и ручные проверки

Из корня проекта:

- `npm.cmd test` — валидация банка, независимое редактирование текстов, сочетания голосов по шести осям, маршруты каждой длины 12–24, удаление и повторное появление вопросов, 1000 воспроизводимых случайных сессий, все 64 соответствия и локальные файлы фото.
- `npm.cmd run test:browser` — Playwright через установленный Google Chrome; требуется работающий Vite на `http://127.0.0.1:5173`. Переменная `TEST_URL` задаёт другой адрес, `BROWSER_CHANNEL` — другой установленный канал браузера. Проверяются короткий/максимальный маршруты, возврат/пересчёт, удаление ответов, новый старт, диалоги, ошибки и повторная загрузка, все вопросы на пяти ширинах. Снимки сохраняются в `artifacts/`.
- `npm.cmd run check:ui` — реестры цветов, текстовых стилей и структура CSS.
- `npm.cmd run build` — TypeScript и готовая сборка.

Браузерная автоматизация не заменяет ручную проверку на iOS/Android (M3). Сохранение и восстановление — M4, офлайн-работа и установка — M5.

Технические источники: [локальный сервер и команды Vite](https://vite.dev/guide/), [локальный просмотр сборки](https://vite.dev/guide/static-deploy.html), [настройки сетевого доступа](https://vite.dev/config/server-options.html), [условия установки PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

## Git и размещение

Git уже инициализирован. `.gitignore` исключает `archive/`, офисные документы, PDF, TXT, CSV, зависимости, результаты сборки и локальные служебные файлы. Markdown-документация, рабочие JSON и фотографии приложения остаются доступными для версионирования.

**GitHub — хранение кода; Netlify — публикация принятой версии.** Локальный запуск и тестирование не требуют ни отправки кода, ни развёртывания сайта. Промежуточные просмотры по localhost и локальной сети не создают развёртываний Netlify.

Репозиторий GitHub можно подключить отдельно от хостинга, когда потребуется сохранять код удалённо. Это само по себе не должно публиковать приложение. Netlify подключается для выпуска готовой версии после приёмки и отдельной явной просьбы пользователя.

Для первого выпуска предпочтительна ручная загрузка проверенной папки `dist/`: она позволяет публиковать только выбранную сборку. GitHub при этом может использоваться для хранения исходного кода без подключения автоматических развёртываний. Если позднее выбрана интеграция Netlify с GitHub, заранее согласовать правила выпуска; автоматические production-развёртывания, Deploy Previews и развёртывания веток без отдельного решения не включать. Каждый следующий выпуск готовить и проверять локально до публикации.

Коммиты, отправка кода и публикация — отдельные действия, каждое выполняется только по явной просьбе пользователя. Не публиковать промежуточные версии ради обычного просмотра или тестирования.
