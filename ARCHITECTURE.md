# Архитектура и техническая реализация

Этот документ описывает, **как реализуется текущая версия**: среду, стек, архитектуру, запуск, проверки и размещение. При смене среды разработки технические решения можно пересмотреть, сохраняя требования приложения.

- Требования и утверждённые вопросы: [спецификация](automotive_book_of_changes_spec.md).
- Дизайн-система и внешний вид: [UI_SPEC.md](UI_SPEC.md).
- Порядок работ и состояние приёмки: [TODOs.md](TODOs.md).
- Фактическая схема существующего каталога: [data/README.md](data/README.md).

## Состояние реализации

Промежуточный экран перед уточнениями удалён из маршрута и меню M1. После второго демонстрационного основного вопроса сразу открывается уточняющий; «Назад» возвращает на второй основной. В полной реализации после вопроса 12 маршрут выбирается алгоритмом: результат при шести определённых битах либо первый необходимый уточняющий. На уточнениях вместо названия основного этапа показывается «УТОЧНЯЮЩИЕ ВОПРОСЫ» без числового счётчика; верхняя строка — «Вносим окончательную ясность», шкала из 12 сегментов начинает отсчёт заново. Отдельная реализация алгоритма этим изменением не добавляется.

В M1 подготовлен визуальный прототип приложения: приветствие, два примера основных вопросов, уточняющий и прямой вопросы, демонстрационная карточка Fiat 500 (`000-011`). Маршрут сокращён и фиксирован, алгоритм интервью ещё не реализован; ответы хранятся только в памяти текущей страницы. Сохранение между запусками и PWA относятся к следующим этапам.

Подготовленный каталог и галерея остаются отдельными материалами. Git подключён к `https://github.com/Irina-404/car-i-ching.git`; начальное состояние отправлено в `main`. Публикации приложения нет. Приёмка M1 отражается в TODOs.

Решения ниже задают направление разработки. Наличие инструмента в этом документе не означает, что зависимость уже установлена или соответствующий код написан. Реальный ход работ отражается в TODOs.

### Организация оформления

Дизайн-система, семья шрифта, размеры, цвета, компоненты и адаптивность описываются в [UI_SPEC.md](UI_SPEC.md). В архитектуре фиксируются только способы реализации этих решений.

- Стили находятся в `src/styles.css`; общие размеры и цвета задаются CSS-переменными. Все базовые коды трёх палитр и производные через `color-mix(in srgb, …)` собраны в `src/palettes.css` по UI_SPEC. Компоненты используют именованные цвета. Тема задаётся атрибутом `data-palette` корневого элемента; вместе с ней меняются `color-scheme` и метатег `theme-color`. При загрузке выбрана палитра `graphite`, выбор темы между запусками не сохраняется. Определения начертаний — в `src/fonts.css`, импортируемом из точки входа приложения.
- Manrope подключён локально через `@fontsource-variable/manrope` 5.3.0. Два WOFF2 для кириллицы и латиницы весят около 39 КБ; внешних запросов к Google Fonts нет.
- Лицензия шрифта копируется в сборку как `assets/Manrope-LICENSE`. При реализации PWA используемые файлы шрифтов включаются в офлайн-ресурсы вместе со стилями.
- Главная страница вынесена в `src/HomePage.tsx`; её стили ограничены классами `home-*` и не меняют вопросы и результат. Параметры оформления заданы переменными `--home-*`. Hero преобразован из исходного PNG в WebP с качеством 90 без изменения размеров (1672 × 941, 213 622 байта); SVG сохранён отдельным файлом и окрашивается через CSS-маску без изменения исходника. Главная использует Arial из эталона v8, остальные экраны — локальный Manrope. Исходники и HTML-эталон остаются в `design/` и в сборку не включаются.
- В M1 шапка интервью, вопросы, карточка и диалоги реализованы в `src/App.tsx`; разбиение на компоненты можно уточнить в следующих этапах без изменения требований и дизайн-системы.

## Подключение подготовленного контента

`loadResult(code, signal)` в `src/prototype.ts` загружает запись по произвольному ключу `RRR-CCC`: проверяет формат, связи, обязательные поля и локальный путь фото. Возвращает код, биты, тексты, автомобиль, источник/автора/лицензию и шесть предпочтений из `axisWording`. Функция `loadDemoResult` только вызывает её с `000-011` для M1; сам компонент результата не знает названия Fiat и не вычисляет код по ответам. После M2–M3 вызывающий код передаст вычисленный ключ вместо демонстрационного.

Результат отрисовывается отдельной веткой `App` без прежнего каркаса и служебной панели. `data-view` и `theme-color` меняют фон окна и браузерной панели на светлый, после выхода восстанавливается игровая тема. SVG гексаграммы использует `y = 48 − 8 × index` для битов в исходном порядке: первый внизу, шестой наверху. SVG имеет `viewBox="0 0 60 60"`, CSS-размер 60 × 60 px, полосы высотой 4 px и `shapeRendering="crispEdges"`; координаты кратны целым CSS-пикселям. Существующий Header 1 главной вынесен в `.type-heading-1` и применяется также к архетипу без изменения вида главной. Header 2 `.type-heading-2` используется для разделов главной и автомобиля; настройки шрифта не дублируются в стилях карточки. Существующий диалог получает предпочтения из текущей записи. Возврат на главную не очищает её; новое нажатие «Начать игру» теперь очищает ответы и открывает первый вопрос, поэтому прежний результат не открывается повторно вместо новой игры. Предупреждение при выходе с первого вопроса ещё относится к M3. Диалог «Пройти ещё раз» удалён вместе с этой кнопкой как не входящий в v5.

- Каталог хранится в пяти JSON папки `data/`. Назначения из `placements.json` связывают клетку с автомобилем и фотографией; тексты берутся из `descriptions.json`.
- Подробное описание полей находится только в [справочнике данных](data/README.md). Не создавать вторую редактируемую копию каталога; сборка может копировать ресурсы автоматически.
- Формат ключа клетки — `RRR-CCC`: оси 1–3 слева направо образуют `RRR`, оси 4–6 — `CCC`. Позиции в `structure.json` считаются отдельно внутри каждой триграммы.
- До интеграции проверить 64 уникальных результата, полноту связей и необходимые поля. Отсутствующие значения не угадывать.
- Фотографии находятся в `assets/images/cars/`; поля `url` и `full` содержат пути относительно корня текущей галереи. При сборке приложения обеспечить корректное разрешение этих путей по адресу публикации.
- Галерея и её скрипты — отдельный инструмент просмотра подготовленной базы, не часть приложения интервью. Интерфейс приложения создаётся самостоятельно: он использует JSON и фотографии напрямую, не зависит от HTML галереи или `gallery.js`, не содержит экрана галереи и не включает её в сборку. Подробная карточка автомобиля служит образцом результата по разделу 6 спецификации; её разметку и стили адаптировать в самостоятельный компонент. Общую вводную фразу брать из `descriptions.json → resultUi.twinIntro`.

## Банк вопросов

`InterviewScreen.tsx` объединяет все виды вопросов прототипа (бывший `CoreInterview.tsx`). Этап определяется по роли вопроса; номер передаётся из маршрута. Для M1 позиции основных — 1 и 2, дополнительных — 1 (уточняющий) и 2 (прямой). В полном интервью номер дополнительного вопроса должен вычисляться по реально показанному маршруту, а не ID оси или роли. Прямые вопросы продолжают ту же шкалу; известен максимум 12, не фактическая длина этапа. Служебная панель и старая шапка скрыты на всех вопросах. Область ответов сохраняет резерв под три карточки даже при двух вариантах, чтобы навигация оставалась на месте; скрытая подсказка собственного места не занимает. Заголовок этапа имеет одинаковую минимальную высоту с числовым счётчиком и без него.

Принятое оформление основных вопросов и политика сессии разделены: в M1 возврат с первого вопроса пока не требует подтверждения и сохраняет ответы в памяти, кнопка главной теперь всегда начинает новое прохождение с очисткой ответов. Это допустимое ограничение прототипа. Для приложения в M3 реализовать предупреждение о потере данных перед выходом с первого вопроса: подтверждение очищает сессию и открывает главную, отмена сохраняет её. «Начать игру» на главной всегда создаёт чистую сессию. В M4 очистка должна затрагивать постоянное хранилище и не допускать восстановления удалённой сессии. Восстановление при обычном повторном запуске открывает сохранённый шаг/результат напрямую. Источник правил — разделы 1.1, 3.4 и 7 спецификации.

В `.interview-copy` две строки CSS Grid: растягиваемая область преамбулы сверху и отдельная область H1 перед карточками. Высота H1 зарезервирована переменной `--interview-prompt-height`; общие минимальные высоты текста и карточек — `--interview-copy-height` и `--interview-choice-height`, с порогами 360 и 600 px по UI_SPEC. Размеры измерены по всем 12 основным вопросам без подключения полного банка к прототипу. При обычном масштабе верхняя граница H1, карточки и навигация постоянны; короткая преамбула оставляет свободное место над H1. Никакого вычисления высоты по текущему вопросу, внутренней прокрутки и обрезки текста нет; при увеличенном шрифте минимальные высоты допускают рост содержимого.

Экран основных вопросов M1 получает вопрос, его номер, выбранный ответ и обработчики из `App.tsx`; не вычисляет биты и маршрут самостоятельно. Данные выбора остаются в родительском состоянии, кнопки карточек имеют `aria-pressed`. Наличие нейтрального ответа проверяется по варианту «В» текущей демонстрационной записи, не по названию этапа; при подключении полного банка использовать его семантическое значение N. Подтверждение защищено от повторного вызова до смены вопроса, двойного клика мышью и удержания клавиши. Прокрутка и фокус заголовка обрабатываются существующим переходом в App.

На основных вопросах служебная панель и старая шапка не отрисовываются; экран содержит собственный компактный футер. Главная и прочие экраны не менялись. M1 по-прежнему содержит только вопросы 1 и 2 из основного блока, затем сразу демонстрационный уточняющий вопрос, без промежуточного экрана. Это не полное прохождение 12 вопросов. Вычисления гексаграммы и реальной ветвящейся логики пока нет; полная интеграция, пересчёт устаревших уточнений, сохранение между запусками и корректный вычисленный результат проверяются в M2–M4. Пояснения об ограничениях хранятся в документах, на новый экран служебный текст не добавляется.

Банк будет отдельным JSON в `data/`. Полный утверждённый текст находится только в разделе 5 спецификации; перенос выполняется без перефразирования.

В M1 используется отдельная демонстрационная выборка `src/prototype-questions.json` с вопросами `1.1`–`1.4`. Тексты извлечены из спецификации без перефразирования; вводная ситуация и выделенный вопрос разделены для оформления. В M2 выборку заменить полным банком по схеме ниже. Выборка M1 не содержит вычисления битов.

Рабочая схема записи (пример, не полный банк):

```json
{
  "schemaVersion": 1,
  "language": "ru",
  "axes": [
    {
      "id": 1,
      "key": "scope",
      "questions": [
        {
          "id": "1.1",
          "role": "core1",
          "prompt": "У тебя есть возможность принять участие в одном из двух мероприятий. Оба посвящены интересной тебе теме и проходят в одинаково удобных условиях. Какое ты предпочтёшь?",
          "options": [
            { "code": "A", "value": 0, "text": "Небольшую встречу, где ты знаешь почти всех участников." },
            { "code": "B", "value": 1, "text": "Открытое мероприятие для широкой аудитории, где много незнакомых людей." },
            { "code": "C", "value": null, "text": "Оба варианта одинаково привлекательны." }
          ]
        }
      ]
    }
  ]
}
```

Технические соглашения:

- `schemaVersion` — версия формата; `language` — `ru`.
- Шесть осей с ID 1–6; четыре вопроса на ось, роли `core1`, `core2`, `clarifier`, `forced`; ID вопросов `1.1` … `6.4` сохраняются при редактуре текста.
- `A.value = 0`, `B.value = 1`, `C.value = null`. Код `C` соответствует кириллической кнопке «В»; не выводить технические латинские коды вместо русских обозначений.
- Валидатор проверяет состав осей, роли и ID, число вариантов, значения и полноту текстов. Неполный пример схемы не должен попадать в приложение как полный банк.
- Версию формата отличать от совместимости содержания: правки только формулировок не инвалидируют сессию; изменение значения ответа или структуры маршрута требует отдельной проверки совместимости.

## Архитектура интервью и сессии

Отделить загрузку и валидацию данных, чистую логику интервью, сохранение сессии и компоненты интерфейса. Не проводить ненужный рефакторинг инструмента галереи.

Предпочтительные интерфейсы логики; имена можно уточнить при реализации:

```text
getNextQuestion(answers, questionBank) -> question | null
resolveAxis(axisId, answers) -> 0 | 1 | unresolved
resolveProfile(answers) -> sixBits | incomplete
lookupCar(sixBits, existingCatalog) -> existingCatalogEntry
```

Правила голосования и порядок вопросов берутся из спецификации, не определяются заново здесь. После изменения ответа маршрут вычисляется повторно; неактуальные дополнительные ответы исключаются из расчёта и согласуются с сохраняемым состоянием.

Локальная запись сессии должна содержать ответы, текущий шаг и данные о версии/совместимости. Конкретное браузерное хранилище и формат записи выбираются при реализации; требования восстановления заданы в спецификации.

Гексаграмма вычисляется из кода. Пояснение использует `descriptions.json → axisWording`: `row` для осей 1–3 и `column` для осей 4–6; бит выбирает одну формулировку из пары. В прототипе порядок линий снизу вверх соответствует осям 1→6; оси 1–3 образуют нижнюю триграмму. Бит 0 — разорванная линия, бит 1 — сплошная. Пояснение прототипа относится к фиксированной карточке Fiat 500, а не к выбранным демонстрационным ответам.

## Фотографии и отображение

- Текущие 64 файла — WebP, качество 80, длинная сторона не более 960 px. Маленькие исходники не увеличиваются; пропорции сохраняются, обрезка не применяется.
- Общий размер коллекции — 4 651 542 байта, приблизительно 4,65 МБ.
- При повторном кодировании брать исходные снимки из архива, а не уже сжатые WebP. Два архивных исходника имеют формат JPEG XL и требуют декодирования перед обработкой.
- В новой карточке v5 изображение использует `width: 100%; height: auto` и собственное соотношение сторон. Прежняя фиксированная область 4:3 отменена; снимки не кадрируются и не растягиваются.
- Для проблемных снимков обсуждать адресные исправления; не вводить 64 индивидуальных CSS-исключения для масштаба и положения автомобилей.
- Сведения об источнике, авторе и лицензии сохранять при изменении путей и кодировании.

## Сборка, PWA и обновления

- В опубликованную сборку включать интерфейс, вопросы, каталог и все 64 оптимизированные фотографии. Архив, исходные снимки и инструменты подготовки контента не включать.
- Manifest, иконки и service worker обеспечивают установку и офлайн-работу. Полный набор ресурсов кэшировать так, чтобы после подготовки были доступны любые результаты, а не только уже открытая карточка.
- Проверять завершение подготовки офлайн-ресурсов и обрабатывать прерванную загрузку. Механизм обновления должен предотвращать смешивание несовместимых версий ресурсов и данных сессии.
- Конкретные имена файлов и стратегии кэширования зафиксировать после реализации, не выдавать план за уже работающее поведение.

## Запуск и проверки

### Уже доступно: галерея

Из корня проекта выполнить `node serve-gallery.cjs` и открыть http://127.0.0.1:8765. В Windows также можно запустить `Start-Gallery.cmd`. Требуется Node.js. Сервер слушает только этот компьютер; остановка — Ctrl+C.

Галерея читает JSON напрямую, без сборки: после изменения данных обновить страницу. Прямое открытие HTML через `file://` не загружает JSON из-за ограничений браузера. Локальный сервер отдаёт корректные MIME-типы WebP и других поддерживаемых изображений.

### Промежуточные версии приложения: локальный Vite

Основной способ просмотра на всех майлстоунах — **локальный сервер Vite**. VS Code используется как редактор и место запуска терминала; сайт открывается в обычном браузере. Расширение Live Server не требуется: обработку React и TypeScript обеспечивает Vite.

Node.js и npm уже доступны на этом компьютере. Конфигурация приложения, зависимости и команды ниже подготовлены в M1. Установка зависимостей в текущей рабочей папке уже выполнена.

Порядок просмотра в Windows:

1. Открыть папку `C:\Work\Autos` в Visual Studio Code.
2. Открыть встроенный терминал: «Терминал → Создать терминал». Он должен находиться в папке проекта.
3. При первоначальной настройке выполнить `npm.cmd install`. Повторять установку нужно только при изменении зависимостей; при обычном просмотре этот шаг пропускается.
4. Выполнить `npm.cmd run dev`. Команда запускает Vite на `http://localhost:5173` и открывает браузер.
5. Оставить терминал работающим. При сохранении изменений страница автоматически обновляется; новые сборки и публикация для этого не нужны.
6. Остановить сервер сочетанием Ctrl+C в терминале. Для следующего просмотра снова выполнить команду запуска.

`npm.cmd` в Windows позволяет не зависеть от разрешения запуска PowerShell-скрипта `npm.ps1`; при работающем `npm` команды эквивалентны. Vite настроен на фиксированный порт 5173 с `strictPort`: если порт занят, он показывает ошибку, а не незаметно открывает другой адрес. Если прототип уже запущен, достаточно открыть его адрес; второй сервер не нужен.

Для повседневного просмотра есть **`Start-App.cmd`** в корне: он переходит в папку проекта, проверяет наличие Node.js и зависимостей, запускает тот же сервер и открывает браузер. После первоначальной установки зависимостей достаточно двойного щелчка. Окно сервера остаётся открытым до окончания просмотра и показывает ошибки, если запуск не удался. Это отдельный запуск приложения; `Start-Gallery.cmd` продолжает открывать галерею.

### Проверка готовой сборки локально

Для просмотра готовой сборки доступны команды:

```powershell
npm.cmd run build
npm.cmd run preview
```

Первая создаёт готовую сборку в `dist/`, вторая открывает её на локальном сервере `http://localhost:4173` (также фиксированный порт). Перед каждым просмотром изменённой сборки её нужно пересобрать. Preview служит проверке сборки на компьютере, а не публичным production-сервером. Обе команды работают без GitHub и Netlify.

В M1 `build` проверяет TypeScript и создаёт сборку. Из общего контента копируются только JSON каталога и 64 оптимизированные фотографии; архив, Markdown-документы и рабочая галерея в `dist/` не попадают. Каталог и фотографии не дублируются в исходниках приложения.

PWA ещё не реализовано. На этапе M5 проверять его на собранной версии через preview: установка, подготовка всех ресурсов, повторный запуск без сети и восстановление сессии. В режиме редактирования не включать постоянный service worker, который мог бы подменять свежие файлы старым кэшем. Для приложения и preview используются разные адреса; их хранилища и сессии независимы.

### Просмотр на телефоне

Для ежедневной проверки сначала использовать мобильный режим инструментов разработчика в браузере компьютера. Для просмотра на настоящем телефоне в той же доверенной Wi-Fi-сети предусмотреть `npm.cmd run dev -- --host 0.0.0.0` и открытие `http://<локальный-IP-компьютера>:5173` на телефоне. Компьютер должен быть включён, сервер запущен, а локальный доступ разрешён брандмауэром. Это просмотр по локальной сети без туннелей и публикации в интернете.

Просмотр по обычному HTTP в локальной сети позволяет проверять оформление и интервью, но **не заменяет проверку установки и офлайн-PWA на телефоне**. Для неё нужен защищённый адрес. В M5 при необходимости подготовить локальный HTTPS для собранного приложения с сертификатом, которому доверяет телефон. Адрес `localhost` телефона относится к самому телефону, а не к компьютеру. Публичная промежуточная публикация на Netlify для этого не планируется.

### Автоматические и ручные проверки

Vitest проверяет алгоритм, структуру банка и все 64 сопоставления; Playwright — прохождение, возврат, восстановление и карточки. Команды тестов добавить при создании конфигурации приложения. Проверки PWA выполняются также на целевых телефонах. Полный перечень ожидаемого поведения находится в критериях приёмки спецификации; этапы этих проверок — в TODOs.

Технические источники: [локальный сервер и команды Vite](https://vite.dev/guide/), [локальный просмотр сборки](https://vite.dev/guide/static-deploy.html), [настройки сетевого доступа](https://vite.dev/config/server-options.html), [условия установки PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

## Git и размещение

Git уже инициализирован. `.gitignore` исключает `archive/`, офисные документы, PDF, TXT, CSV, зависимости, результаты сборки и локальные служебные файлы. Markdown-документация, рабочие JSON и фотографии приложения остаются доступными для версионирования.

**GitHub — хранение кода; Netlify — публикация принятой версии.** Локальный запуск и тестирование не требуют ни отправки кода, ни развёртывания сайта. Промежуточные просмотры по localhost и локальной сети не создают развёртываний Netlify.

Репозиторий GitHub можно подключить отдельно от хостинга, когда потребуется сохранять код удалённо. Это само по себе не должно публиковать приложение. Netlify подключается для выпуска готовой версии после приёмки и отдельной явной просьбы пользователя.

Для первого выпуска предпочтительна ручная загрузка проверенной папки `dist/`: она позволяет публиковать только выбранную сборку. GitHub при этом может использоваться для хранения исходного кода без подключения автоматических развёртываний. Если позднее выбрана интеграция Netlify с GitHub, заранее согласовать правила выпуска; автоматические production-развёртывания, Deploy Previews и развёртывания веток без отдельного решения не включать. Каждый следующий выпуск готовить и проверять локально до публикации.

Коммиты, отправка кода и публикация — отдельные действия, каждое выполняется только по явной просьбе пользователя. Не публиковать промежуточные версии ради обычного просмотра или тестирования.
